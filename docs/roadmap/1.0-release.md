# 1.0 release

[← Back to the checklist](../../ROADMAP.md#10-release)

1.0 is a promise, not a feature count. It tells users that their data survives every later
update, that `config.toml`, the export format and the plugin API will not break without a
major version, and that the build they install is signed and updates itself. The workspace
is at `0.1.1`. Everything below is the line between that and `v1.0.0`; items in the phases
are referenced rather than repeated.

## Scope decisions (settle first)

### Is P2P in 1.0?

Decision (owner, 2026-10-19): no. Ship 1.0 as a single-machine product and put company sync behind a "Preview" switch that is off by default. Sync v2 (Phase 5) is a rewrite of the transport and the data layer, and today's Tor path does not work end to end, so holding 1.0 for it would hold everything else. Data-loss fixes in the current P2P path still land now; P2P itself is not a 1.0 promise. The exception is the **stock ledger** (Phase 4): it changes the database's data model, so it must land before 1.0, or 1.0 freezes the model Sync v2 has to migrate away from.

### Credential model: customers bring their own API keys

(owner decision, 2026-10-19). Nisaba's own application for Amazon SP-API keys was denied, so there is no shared Amazon app to broker. Every customer enters their own eBay developer keyset, their own Amazon SP-API app (LWA client id and secret plus a refresh token), their own Squarespace API key and their own XMR Bazaar login. This is what the code already does. Amazon, Squarespace and XMR Bazaar stay bring-your-own, and the setup wizard (*Gate: product*) carries that onboarding cost. **Revised 2026-10-28 (owner decision): eBay is the exception.** 1.0 ships one-click eBay sign-in through a small hosted OAuth broker holding Nisaba's own eBay keyset, because eBay is where bring-your-own costs the most (see *One-click eBay sign-in* under *Gate: product* and *Services*). Bring-your-own eBay keys stay available as an advanced option.

### Which adapters are "1.0"?

Decision (owner, 2026-10-19). An adapter ships as stable only after a live-account verification (below). Anything not verified ships labelled *Beta* in the UI, or disabled. **Amazon ships as Beta:** each customer must get their own SP-API developer registration approved (bring-your-own SP-API keys), Amazon can refuse it as it refused ours, and the adapter has never been verified end to end. The other adapters (eBay, Squarespace, XMR Bazaar) ship as stable only if the live-account verification below is recorded for them; otherwise they too ship labelled *Beta* or disabled. The setup guide says so before the customer starts.

## Gate: security

### Plugin re-approval on code change, and plugin secrets in the keyring (Phase 3)

Closed 2026-10-25 after checking the code: both halves shipped in Phase 3. A re-import or
re-submit whose code or allowlist changed resets the plugin to `pending` with the new
`code_hash` (`commands/vendors.rs`), a P2P merge does the same (`crates/p2p/src/sync.rs`),
and the run paths refuse a plugin that is not `approved`. `secret: true` values are stored
in the OS keyring (`nisaba-plugin-config`, `crates/core/src/crypto.rs`), and
`crates/p2p/tests/plugin_secrets_excluded.rs` asserts they stay out of `config_json` and
the P2P payload.

### Secret-handling audit closed

Nothing secret in `config.toml`, logs, exports or P2P payloads (Cross-cutting).

### Tauri capabilities narrowed so the main window can invoke only the commands it uses, and secret-returning commands are reachable only from the settings views that display them

Status 2026-10-28, kept open after checking the code. The second half is done another
way: no command returns a secret to any webview. `get_config`,
`get_company_platform_config` and `get_vendor_plugin_config` mask stored secrets
(`crates/core/src/masked.rs`) and saves keep a masked value as it is, and the company secret
is only shown in a native dialog or copied to the clipboard from Rust. Settings therefore
live in the main window, which is the only window with a capability, and
`crates/tauri-app/src/acl_check.rs` keeps its allow list equal to the registered
commands. The first half is not done: the main window can invoke every app command,
including ones only Settings calls (`update_config`, `backup_now`, `restore_backup`).
Narrowing that would close this item.

## Gate: product

### First-run setup wizard

It walks through each platform's credentials, with links to the developer portals, the exact redirect URI (eBay RuName) to register, and a *Test connection* button per platform. Because customers bring their own keys, this is the difference between a tool its author can use and one a seller can. Amazon's step explains the SP-API developer registration (self-authorized private app), the roles to request, and that approval is Amazon's decision.

### Credential health in the UI

Per platform, show when the token or keys expire (eBay's refresh token, Amazon's LWA client-secret rotation), warn ahead of time, and link straight back to the wizard step that renews them (Phase 2's token-expiry item). [N-11.2: `get_credential_health` command + credential-health panel (dashboard alerts, settings full view, status-bar warnings); eBay persists `refresh_token_expires_in` to `auth_tokens.refresh_token_expires_at` (migration 029); Amazon stamps `client_secret_updated_at` on secret change and warns past the 365-day rotation window; mid-sync `refresh_auth` failures surface as a persistent banner via the `AuthExpired` event; warnings deep-link to `/setup?platform=…` (N-11.1 wizard step).]

### Empty and error states, confirmation of destructive actions, and the silent-startup fix (Phase 7)

[N-11.5: `main.rs` no longer `expect()`s on config load, DB open, migrations, the rustls provider install, or `Builder::run` — failures go through `startup::fatal_startup_error`, which writes a timestamped log to `<data dir>/logs/startup-errors/` (`%APPDATA%\nisaba\…` on Windows, `~/.config/nisaba/…` on Unix), shows a native OS error dialog (MessageBoxW / osascript / zenity-kdialog) naming the failing stage, and exits non-zero. Unit tests cover the report text and log-file writing.]

### Export diagnostics

One button that zips recent logs, versions, the platform and the redacted config for a bug report. This replaces any telemetry or crash-reporting service (see *Services*). [N-11.4: `export_diagnostics` command builds `nisaba-diagnostics.zip` (`versions.json`, `logs.txt`, `config.redacted.json`) via a save dialog; every secret value is replaced with `[REDACTED]` by key *and* scrubbed from the log text; unit tests assert five known secret values appear nowhere in the bundle. Button lives on the new Settings → About view (`frontend/pages/about.vue`, also openable from the main nav), next to the app version from `get_app_version`.]

### One-click eBay sign-in through a hosted OAuth broker (shared eBay keyset)

Today every customer registers their own eBay developer app and pastes a client ID, client secret and RuName. "Authorize with eBay" cannot work without those, because eBay's authorize URL needs the client ID and the token exchange and every refresh need the client secret. One-click therefore needs Nisaba to own a keyset, and the secret cannot ship in the public repo or the app. See *Shared eBay keyset and hosted OAuth broker* in *Services* for the design, the prerequisites only the owner can do, and the open questions.

Done when: a new customer connects eBay with the "Authorize with eBay" button alone, the three credential fields sit behind a "Use my own keys" option, a recorded live-account run covers authorize, fetch and refresh through the broker, and the stability and privacy statements describe the broker.

## Gate: legal and platform terms

### Third-party license notices bundled in the app

An *About → Licenses* view generated by `cargo-about` (Rust) and a license checker (npm). Most dependencies are MIT or Apache-2.0, and both require shipping their notices with binaries.

### Each platform's API terms reviewed against what Nisaba does

eBay's API License Agreement, Amazon SP-API's Acceptable Use and Data Protection policies (relevant as soon as order data with buyer details is read), Squarespace's API terms, and XMR Bazaar's terms on automated access, since that adapter scrapes HTML. [N-12.4: reviewed 2026-10-23; recorded in `docs/roadmap/platform-terms-review.md` with behaviour-change follow-ups: Amazon 429/backoff audit, Squarespace User-Agent check, XMR Bazaar residual-risk guide note, and a re-review trigger rule for any future order/buyer-data access.]

### eBay **Marketplace Account Deletion** notifications

Every production keyset must either subscribe an HTTPS endpoint or be granted an exemption for not storing eBay user data. A customer using their own keys does this for their own keyset, so the setup guide must walk through the exemption. The shared keyset needs the same subscription or exemption done once by Nisaba; a stateless broker that stores no eBay data is likely to qualify for the exemption, but confirm that with eBay. Confirm the current rule with eBay before writing the guide. [N-12.1: rule confirmed against eBay's current developer docs (subscribe or opt out before the first production call; keyset activated only after); the walkthrough ships in the in-app guide as `frontend/public/guide/ebay-deletion.html`.]

What leaves the machine (update checks, marketplace API calls, P2P relays if enabled) and what never does. [N-12.4: shipped as `PRIVACY.md` at the repo root, linked from README, and in the app as `frontend/public/guide/privacy.html` with an index card.]

## Stability contract at 1.0

### Write down what is frozen and how it versions

- the plugin API (`api_version` 1; Phase 3);
- `config.toml` (a `config_version` key, with migration on load);
- the export format (versioned, imports every earlier 1.x);
- the database (forward-only migrations, backup first);
- the P2P protocol (versioned, if P2P is in).

Plus a deprecation policy: a deprecated surface keeps working for at least one minor
release, with a warning in the UI.
