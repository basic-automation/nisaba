Backups and restore

Your catalog, mappings, credentials, and sync history all live in one SQLite database file. Nisaba backs it up automatically — and lets you take manual snapshots and restore any of them from the UI.

Automatic backups

  • Before every migration. Whenever an app update changes the database schema, Nisaba writes a backup first, so a failed or unwanted upgrade can always be undone.
  • On a schedule. Enabled by default: a backup every 24 hours, keeping the newest 7. Both the interval and the retention count are configurable under [database] in config.toml (interval_secs, keep_last).
  • Before a restore. Restoring a backup first takes a safety snapshot of the current database, so a restore is itself reversible.

Backups land in <database-folder>/backups unless you set a different dir in the config. Pruning always keeps at least the newest backup, even if you set keep_last to 0.

Manual backups

Use Back up now (Settings → About → Backups, or the backup control in your database settings) before doing anything risky: bulk edits, remapping a platform, or upgrading. The snapshot is written immediately and appears in the backup list.

Restoring

  1. Open the backup list and pick the snapshot to return to. Check its timestamp — pick the newest one from before the problem started.
  2. Choose Restore. Nisaba first writes a safety snapshot of the current database, then replaces it with the backup.
  3. The app restarts to reopen the database cleanly. Verify the data, then re-run a sync cycle to bring the platforms back in line with the restored catalog.

Restore is a rewind, not a merge

Restoring replaces the entire database with the backup: catalog, mappings, credentials, and history all go back to that moment. Anything changed since — new products, new mappings, credential updates — is gone unless it exists in a newer backup. Export anything important before you restore.

Keep an off-machine copy

Automatic backups protect you from app bugs and bad edits, but they live on the same disk as the database. Copy the backups folder (or at least the newest snapshot) to external storage or a cloud drive periodically — disk failure is the one thing local backups can't survive.
